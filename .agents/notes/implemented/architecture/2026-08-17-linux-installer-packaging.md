# Agent Note: Linux installer packaging

Status: implemented

English | [中文](2026-08-17-linux-installer-packaging.zh.md)

## Decision

`dsh-plugin-desktop/scripts/package-linux.ts` gives DSH Desktop a `yarn dist:linux` command that produces deb, rpm, and AppImage installers for Linux x64 in one invocation, shaped like `package-win.ts` and `package-mac.ts`: it rejects non-Linux hosts, non-x64 architectures, and any Node release other than 22.19+ or 24.x, runs `check:linux-package` (the build, every TypeScript compiler face, the packaging- and runtime-focused test files, and the runtime-closure verifier), invokes Electron Builder once with `--linux deb rpm AppImage --x64`, and finally verifies all four resulting artifact paths and their file-format magic numbers through `verify-linux-installer.ts`. A single script covering all three targets was chosen over three per-format sub-scripts because Electron Builder packs `linux-unpacked` once internally no matter how many Linux targets one CLI invocation requests; three sub-scripts would each redundantly re-run that same pack step, and a sub-script that silently produced fewer than its own target would not be caught by the other two. One command that either produces all three verified artifacts or throws is fail-loud; three commands that can each partially succeed is not.

Linux packaging touches none of `dsh-plugin-desktop/src/`. Three platform-gated restrictions on desktop-only capability already existed before this work and needed no change: the packaged terminal plugin is disabled on Linux by a `disabled: !!js process.platform === 'linux'` guard in `cordis.patch.yml`, advanced-mode shell composition is explicitly rejected on Linux in `src/index.ts`, and the update flow degrades to a "new version available, but this build has no download" prompt through the existing `canDownload` check in `src/electron-runtime.ts` / `src/updates.ts`. Linux installer packaging is therefore a packaging-layer change only — `build.linux` targets, an icon set, a packaging script, a verifier, a CI job, and a Docker harness — with zero new runtime code paths.

## Electron Builder configuration

- **`toolsets.appimage: "1.0.3"`.** Electron Builder's default AppImage path downloads the FUSE2 static runtime, whose AppRun injects `--no-sandbox` unconditionally and requires users to install `libfuse2` on newer distributions where it is no longer preinstalled. Electron Builder's own schema description lists `"1.0.3"` under a `Betas:` heading, and the vendor's documented default remains `"0.0.0"` (the legacy FUSE2 path) — this is a deliberate, verified choice to use that non-default, vendor-labeled-beta toolset, not an oversight. Setting `toolsets.appimage: "1.0.3"` selects the static (non-FUSE2) runtime instead, matching the direction Electron Builder v27 defaults to. The schema only accepts `"0.0.0" | "1.0.2" | "1.0.3" | null`; the value `"1.1.0"` mentioned in some Electron Builder v27 documentation is not legal here and is rejected by Ajv validation before packaging starts. Confirmed unchanged (identical enum, identical `"0.0.0"` default, identical `Betas:` grouping) when the repository's pinned `electron-builder` moved from 26.15.3 to 26.15.7 during a later rebase.
- **The icon set is a `build/icons/` directory capped at 512x512, not a single 1024px source.** Electron Builder's single-file icon path performs no scaling — it reads the PNG's real dimensions and emits one `IconInfo` for that exact size, which `FpmTarget` then maps to `/usr/share/icons/hicolor/<size>x<size>/apps/<executableName>.png`. freedesktop's hicolor `index.theme` only declares directories up to `512x512`; a size outside that declared set is not enumerated by spec-compliant icon-theme lookup (GTK `IconTheme`, `gtk-update-icon-cache`). A single 1024px PNG would therefore install into an undeclared `1024x1024` directory and leave `.desktop`'s `Icon=dsh-desktop` unresolved after a deb/rpm install. `scripts/generate-linux-icons.mjs` derives `build/icons/<N>x<N>.png` for N in {16, 24, 32, 48, 64, 96, 128, 256, 512} from the same `build/app-icon.png` source used for Windows. AppImage is unaffected by this ceiling because its desktop integration reads `.DirIcon` and `<executableName>.png`, which `appLauncher.copyIcons` symlinks to the largest available icon directly in the AppDir root rather than going through hicolor lookup.
- **The three `artifactName` values are literal strings, not `${arch}`.** `expandArtifactNamePattern` strips the arch macro entirely when the target arch equals the default arch (x64) and the user has not forced arch naming. `deb` and `rpm` targets carry an internal `isUseArchIfX64 = true` fallback that reinstates the arch segment anyway, but AppImage has no equivalent fallback — its default name would resolve to `DSH Desktop-<version>.AppImage`, with a literal space and no architecture marker. Writing all three names as literals sidesteps that inconsistency and lets `verify-linux-installer.ts` assert three exact, predictable paths the same way `verify-win-installer.ts` does for the NSIS installer.
- **`linux.executableName` must be set explicitly.** `LinuxPackager` falls back to `appInfo.sanitizedName.toLowerCase()` when the field is absent, which resolves to `dsh-plugin-desktop` (the npm package name), not the `dsh-desktop` command name the rest of the product already exposes. The field is Linux-only and does not affect the Windows or macOS executable names; it also determines the `/usr/bin` symlink name, the installed icon filename, and the `.desktop` file's `Icon=` value, so it had to match `dsh-desktop` for those three surfaces to agree.

## CI and the Docker harness

The CI job (`desktop-linux` in `.github/workflows/ci.yml`) pins `runs-on: ubuntu-24.04` instead of `ubuntu-latest` — the first version-pinned job in this repository; every other job still floats on `*-latest`. The `ubuntu-24.04` image preinstalls the apt `rpm` package (`rpm 4.18.2`), which provides `/usr/bin/rpmbuild`, a hard host requirement for the rpm target. The `ubuntu-26.04` image that `ubuntu-latest` will eventually resolve to ships `rpm 6.x`, an unverified pairing with the `fpm 1.17.0` binary that Electron Builder downloads at packaging time; pinning avoids silently inheriting that risk when GitHub rolls the `latest` label forward.

`docker/linux-package/` exists for two reasons CI does not have. First, the development host is Debian-based without `rpmbuild` installed, so packaging locally needs either a one-time `sudo apt-get install rpm` or an isolated, disposable build environment. Second, rpm's actual install behavior — dependency resolution, file layout, icon paths, package metadata — cannot be checked on the development host at all without an rpm-based distribution; the packaging-time verifier only confirms the artifact's own file format, not what happens when a system installs it. The harness's three Compose services split those needs: `package` builds all three artifacts in a Debian 12 container with a matching Node version; `verify-deb` installs the built deb into a clean `ubuntu:24.04` container and asserts the installed layout; `verify-rpm` installs the built rpm into a `fedora:latest` container and does the same. CI deliberately does not adopt this container for its own build: the `ubuntu-24.04` runner already has `rpmbuild` preinstalled, so containerizing would mean installing `rpm` and a native build toolchain (`build-essential`, `python3`) inside a container image on every run — undercutting the exact reason `ubuntu-24.04` was pinned in the first place, and adding build time CI does not need.

## Verified behavior (Task 7)

Install-level verification ran against real distributions, not just packaging-time artifact checks:

- **deb (Ubuntu 24.04, `docker compose run --rm verify-deb`, exit 0).** The fpm/dpkg package name is `dsh-plugin-desktop` (derived from `package.json`'s `name` field), distinct from the `dsh-desktop` executable name (`linux.executableName`). The installed `.desktop` file at `/usr/share/applications/dsh-desktop.desktop` reads:
  ```
  [Desktop Entry]
  Name=DSH Desktop
  Exec="/opt/DSH Desktop/dsh-desktop" %U
  Terminal=false
  Type=Application
  Icon=dsh-desktop
  StartupWMClass=DSH Desktop
  Comment=DSH Desktop: an Electron shell composed as a DeepSeek Harness Cordis plugin
  Categories=Development;
  ```
  `StartupWMClass=DSH Desktop` was auto-generated by Electron Builder, not configured explicitly. The application installs under `/opt/DSH Desktop/` — the space is real, confirmed, and accepted (see Known limitations) — with `/usr/bin/dsh-desktop` as a symlink, confirmed via `update-alternatives`. `chrome-sandbox` was observed at mode `4755` (`-rwsr-xr-x`) in this run because the container's own `unshare -Ur true` userns probe failed (`unshare: unshare failed: Operation not permitted`), so the deb's postinst script chmod'd it to the SUID fallback path. `dpkg-query -W -f='${Package} ${Maintainer}\n'` printed `dsh-plugin-desktop anywhere-labs <anywhere-labs@users.noreply.github.com>`, an exact match.
- **rpm (Fedora 44, `docker compose run --rm verify-rpm`, exit 0).** The `fedora:latest` tag resolved to `Fedora release 44 (Forty Four)` at test time. `rpm -qpi` showed `Packager` and `Vendor` both exactly `anywhere-labs <anywhere-labs@users.noreply.github.com>`. `dnf install -y ./*.rpm` resolved and installed the full dependency tree with zero missing or unresolvable packages — a real, positive confirmation that using Electron Builder's default `depends` list (rather than an override) was sound for this target environment. Install layout matched the deb: `/opt/DSH Desktop/dsh-desktop`, `/usr/bin/dsh-desktop` symlink, icon at `/usr/share/icons/hicolor/512x512/apps/dsh-desktop.png`, no `1024x1024` entry.
- **AppImage (real graphical session on the development host, not a container — containers have no FUSE and no display).** `chmod +x` followed by direct execution launched successfully, with `--enable-sandbox` present in the renderer process's command line: the real Chromium sandbox was active on this host, because this host's ambient session permits unprivileged user namespaces in practice, even though a separate, deliberately isolated `aa-exec -p unconfined -- unshare -Ur true` probe (run standalone, not from inside the AppImage's own process tree) returned exit 1 on this same host. Both code paths are confirmed sound — the static runtime not injecting `--no-sandbox` by default, and AppRun's fallback probe adding `--no-sandbox` only when userns genuinely is not available — this host simply landed in the "sandbox works" branch rather than the fallback branch, and either branch produces a working launch. The app's log file (`~/.config/DSH Desktop/logs/dsh-<date>.log`) wrote the expected boot header line, and Session Storage showed real workspace-view state persisted against the loopback web server, confirming the UI genuinely rendered and initialized a workspace rather than an Electron shell process merely existing. The process was stable for 40+ seconds with no crash, and teardown left no leftover FUSE mount.

## Known limitations

- `/opt/DSH Desktop` contains a literal space. The path is fixed by `sanitizedProductName`; Electron Builder 26.x exposes no installation-prefix option. `.desktop`'s `Exec` line is quoted correctly and the application works, but the path does not follow the usual Debian path convention. Changing it would mean changing `productName`, which also affects macOS and Windows naming and is a breaking change out of scope here.
- deb/rpm `depends` use Electron Builder's own defaults rather than an override. Overriding either list replaces the entire default set rather than extending it, which would make this package permanently responsible for hand-tracking Electron Builder's own dependency list. The default set's transitive closure lacks `libasound2`, `libgbm1`, `libdrm2`, and `libgl1`; an ordinary desktop already has them preinstalled, a minimal system or container image does not.
- Linux packaging needs network access. Electron Builder downloads `fpm@2.1.4` (bundling fpm 1.17.0 and a portable Ruby), the AppImage toolset, and `7zip@1.0.0` at packaging time; there is no fully offline build path without pre-seeding `ELECTRON_BUILDER_BINARIES_MIRROR` / `CUSTOM_FPM_PATH`.
- Containers cannot perform AppImage's graphical launch test. Mounting an AppImage requires FUSE, which is unavailable inside containers, and there is no display to launch a window against either way. `docker/linux-package`'s `verify-deb` and `verify-rpm` services cover install-level verification for those two formats only; AppImage's actual graphical launch was verified solely on the bare host, as described above.
